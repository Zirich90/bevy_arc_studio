# 07. План: ECS-редактор для Bevy из цепочки плагинов

Статус: рабочий план, обновлён 2026-11-02 по запросу владельца.
Раздел 2 — исторический аудит до реализации E0–E6. Текущий статус и следующие этапы приведены в разделе 8.
Первоначальный обзор Bevy 0.19/0.20, Jackdaw и Fyrox выполнен по коду и документации; Jackdaw не запускался.

## 1. Цель и границы
Редактор мира и уровней для Bevy с управлением человеком и ИИ-агентом (BRP). Не «замена Unity».
Требования: кроссплатформенность, ECS-основа (не копия Unity/Fyrox), автономность.
- **ECS-основа**: сцена = `World`; свойства = рефлексия; правки = команды над миром; редактор сам хранит состояние в ECS.
- **Автономность**: зависим только от Bevy и узких библиотек; нет опоры на чужой редактор; формат сцены за нашим интерфейсом.
- **Кроссплатформенность**: Windows, Linux, macOS; CI-сборка на всех трёх; веб/мобильные только как цель экспорта игр, не редактора.
- **Масштаб**: каждый этап даёт проверяемый результат. Общие части (иерархия, инспектор, сцены) только в объёме, нужном плагинам.

Не делаем: графы материалов, частицы/VFX, катсцены, локализацию, свои DLL-плагины «на лету», стриминг больших миров.

## 2. Аудит: что уже есть
Код ~10,5 тыс. строк, `BevyArcStudioPlugin` уже собран цепочкой плагинов (`src/lib.rs`).

| Область | Есть | Оценка для целевой архитектуры |
|---|---|---|
| Команды | `StudioCommand` (Reflect-enum), реестр операторов из рефлексии, типизированные результаты, очередь по BRP (`mcp_commands.rs`, `operators.rs`) | Хорошая основа общего командного канала |
| Откат | `UndoHistory<S>` с транзакциями (`arc_core.rs`); отдельная `SceneHistory` для объектов; правки компонентов через `record_edit` | Несколько историй, нужна единая |
| Сцена | `DynamicWorld` в `.scn.json`, `SceneComponentRegistry`, сайдкар `.heights` (`world_io.rs`) | Рабочий формат; BSN-загрузчика в Bevy ещё нет |
| Инспектор | Универсальный через рефлексию (`ui_reflect.rs`) + специальные вкладки (`ui_inspector.rs`) | Основа есть, вкладки жёстко зашиты |
| Выделение, гизмо | `selection.rs`, свой `gizmo_3d.rs` (672 стр.) | В Bevy 0.19 появился штатный `TransformGizmoPlugin`: сравнить |
| Мир | Террейн, вода, свет/атмосфера, кисти, пропсы (`terrain_*`, `lighting`, `water`, `props`) | Станут плагином «мир» |
| Навигация | `navigation.rs`, `movement.rs` | Общий сервис для плагина уровней |
| Правила | крейт `crates/bevy_arc_pf2e` (`rules/`, `actors/`, `encounter`, `ui_combat`) | Отделены в плагин (E8): спавн-обработчики, inspector overrides, `Custom`-команды |
| UI | egui, 8 файлов `ui*.rs` | Работает; зависимость от egui размазана |

Не нашёл: панель иерархии (outliner) с перетаскиванием, браузер ассетов, префабы, несколько сцен, запуск игры из редактора, единый реестр инструментов и панелей.
Прочее: в `Cargo.toml` включён `dynamic_linking` (годится для разработки; для релиза и Windows нужен отдельный профиль — решение за владельцем, версии в Cargo.toml зафиксированы правилами проекта).

## 3. Целевая архитектура
Ядро `editor` даёт контракты, плагины подключают область:
- **Состояние редактора в ECS**: `EditorSelection`, `ActiveTool`, `EditorMode`, панели как сущности.
- **Команды**: единый канал `EditorCommand` (компонент, ресурс, spawn/despawn, reparent, терреин-патч); одна история на все; тот же канал для UI и BRP.
- **Реестр**: `register_tool`, `register_panel`, `register_scene_component`, `register_inspector_override`, `register_asset_kind`.
- **Плагин** приносит: компоненты (`Reflect`), инструменты (системы), панели (там, где мало инспектора), правила сохранения.
- **UI-слой**: панели читают состояние и пишут команды; egui остаётся реализацией, но ядро не использует его типы.
- **Зависимости плагинов** явные (плагин требует другой); общие сервисы (навигация) вынесены.
- Разделение на крейты — только когда появится второй потребитель; до того модули одного крейта.

Плагины: `world` (террейн, вода, свет, атмосфера), `level` (стены/модули, сетка), `assets` (браузер, префабы), `actors` (pf2e), `dialogue` (позже), `audio` (позже).

## 4. Этапы
Каждый этап: промпт и лог в `docs/clean_room_audit/`, `cargo check --message-format=short -q`, тесты, снимок через `brp_extras/screenshot` в `docs/screenshots/`.

**E0. Базовая линия (S).** Зафиксировать текущее состояние: тесты, снимок, список команд. Решить вопросы раздела 5. CI-матрица Win/Linux/macOS (только сборка и тесты). Приёмка: зелёный CI на трёх ОС.

**E1. Единая история и командный канал (M).** Свести `UndoHistory<WorldSpec>`, `SceneHistory`, `record_edit` к одной истории над `EditorCommand` (компонент, ресурс, spawn/despawn, reparent, патч террейна). Приёмка: тест «смешанная цепочка правок откатывается в обратном порядке»; тот же сценарий через BRP; снимок.

**E2. Иерархия и выделение (M).** Панель outliner (`ChildOf`, `Name`, поиск, переименование, перенос через команду), мультивыделение. Spike: заменить `gizmo_3d.rs` штатным гизмо, если покрывает движение/поворот/масштаб и снап; иначе оставить. Приёмка: перенос сущности в иерархии с откатом; снимок.

**E3. Реестр плагинов, срез №1 (M).** Ввести `register_*`, перевести `world` (террейн, атмосфера) на реестр, убрать зашитые вкладки инспектора. Приёмка: сборка без `world` проходит и запускается; панель мира появляется только с плагином; снимок.

**E4. Плагин уровней, срез №2 (L).** Сетка и снап, расстановка модулей из набора glb, инструмент «стена по линии», обновление навигации через сервис. Приёмка: комната собирается в редакторе, сохраняется, загружается; та же комната собирается агентом через BRP; снимок.

**E5. Ассеты и префабы (L).** Браузер (glb, миниатюры), префаб = сохранённая подсцена с переопределениями; несколько сцен и переход. Spike: BSN или `DynamicWorld` (зависит от состояния загрузчика `.bsn` в Bevy). Приёмка: префаб с переопределением переживает сохранение и загрузку.

**E6. Запуск игры из редактора (L).** Отдельный процесс, связь через BRP, живое дерево сущностей, пауза/стоп. Приёмка: правка компонента в живой игре и возврат в редактор.

**E7. Пилотная игра (M, параллельно с E4+).** Небольшая тактическая сцена на `rules/` и `actors/`: проверяет, каких функций редактору не хватает. Приёмка: играбельный уровень, собранный только редактором.

## 5. Открытые решения (за владельцем)
1. Цель: инструмент как продукт или редактор под конкретную игру (влияет на объём E5–E6).
2. Формат сцены: оставаться на `DynamicWorld` или идти к BSN (в Bevy 0.20 нет загрузчика `.bsn`; запись мира в BSN запланирована на 0.21).
3. `dynamic_linking`: оставить в основных зависимостях или вынести в профиль разработки (правило проекта фиксирует Cargo.toml).
4. Нужна ли проба Jackdaw (день-два) как справочная, до E3.

## 6. Риски и точки пересмотра
- Официальный редактор Bevy (приоритет автора Bevy, сроков нет) может перекрыть часть общей функциональности. Пересмотр после E3 и каждые три месяца: что вышло у Bevy и Jackdaw, что берём взамен своего.
- Формат сцены (BSN) меняется: держать за интерфейсом.
- Плагины компилируются вместе с редактором; загрузка DLL «на лету» откладывается (нестабильный ABI в Rust, лимит экспортов DLL на Windows).
- Две линии работы (генератор мира и общий редактор) делят время: приоритет у того, чего нет у других (мир + управление ИИ).

## 8. Дорожная карта до полноценного редактора — 2026-11-02

Цель: проверенный путь от создания проекта и уровня до выпуска самостоятельной игры.
E0–E6 составляют реализованную основу; E5/E6 приняты по указанному выше логу.
Поведение 3.1–3.3 принято: таймеры, сигналы, Undo, сохранение и Play/Pause/Stop.
Следующий этап — E7. Наличие основы не означает готовность всех возможностей из дальнейших этапов.
Перед каждым этапом проверять текущую реализацию и делать только недостающую часть.

### E7. Пилотная игра — следующий этап

Собрать небольшой тактический уровень на `rules/` и `actors/` средствами редактора:
окружение, игровые участники, настройки столкновения, начало и завершение сценария.
Создание и настройка доступны через UI; агент может повторить основные действия через BRP.
Недостающие возможности фиксировать по конкретным препятствиям пилота, без расширения редактора на будущее.

Приёмка: уровень собран без ручной правки файлов сцены, сохранён, повторно открыт и пройден.
Отдельный игровой процесс, Pause/Resume/Stop и возврат в редактор работают; исходная сцена сохраняется.
Зафиксировать сценарий воспроизведения, обнаруженные пробелы, BRP-проверки и просмотренные скриншоты.

### E8. Сохранность работы

Автосохранение с отдельными восстановительными копиями, восстановление после аварийного завершения,
индикатор изменённого документа и предупреждение перед потерей несохранённых изменений.
Не перезаписывать последний исправный файл при неуспешном сохранении.

Приёмка: после принудительного завершения доступно восстановление; повреждённая копия диагностируется,
исправная сцена сохраняется. Отмена закрытия или перехода оставляет текущие правки на месте.

### E9. Проекты и выпуск самостоятельной игры

Создание и открытие проекта, относительные пути ресурсов, настройка стартовой сцены.
Сборка игрового приложения без панелей редактора, упаковка необходимых ассетов и понятные ошибки сборки.
Отдельный запуск E6 — средство проверки во время разработки, а не готовый экспорт игры.
Начать с Windows; Linux и macOS принимать отдельно на соответствующих ОС.
Версии зависимостей остаются фиксированными. Изменения профилей и упаковки не должны ломать режим разработки.

Приёмка: пилот E7 запускается из отдельной папки без исходного проекта, Cargo и установленного редактора.
В комплекте присутствуют необходимые ресурсы и лицензии; ошибки отсутствующих ресурсов видны пользователю.

### E10. Надёжная работа с ассетами

Импорт и повторный импорт, устойчивые ссылки при перемещении и переименовании через редактор,
диагностика отсутствующих ресурсов. Браузер и миниатюры E5 использовать повторно.
Предварительно проверить существующие идентификаторы и зависимости сцены/префабов; миграцию формата делать явно.

Приёмка: переименование и повторный импорт модели не разрывают ссылки в сцене и связанном префабе;
удаление используемого ассета показывает зависимости, повторное открытие проекта сохраняет результат.

### E11. Расширяемое поведение объектов

Развить принятую модель таймеров и сигналов: условия, триггеры, действия и ссылки на объекты.
Настройка через инспектор, единые команды UI/BRP, Undo/Redo, сохранение и переопределения префабов.
Узловой интерфейс рассматривать только после проверки модели исполнения на пилоте.

Приёмка: цепочка «триггер → условие → действие» работает после сохранения/загрузки;
Pause останавливает исполнение, Stop восстанавливает исходное состояние, неверные ссылки диагностируются.

### E12. Игровые инструменты

Вводить отдельными проверяемыми срезами по потребностям пилота: редактирование коллайдеров,
настройка анимаций, звука, игрового ввода и игрового UI.
Выбор библиотек и изменение зависимостей требуют отдельного решения; заранее новые зависимости не добавлять.

Приёмка каждого среза: объект настроен через редактор, результат переживает сохранение/загрузку
и работает в самостоятельной игре. Параметры доступны агенту через BRP.

### E13. Удобство, диагностика и продуктовая приёмка

Настраиваемое расположение панелей, горячие клавиши, поиск команд, журнал ошибок,
показатели времени кадра и загрузки ресурсов. Проверить типовые размеры окна и масштабирование UI.
Блокирующие ошибки удобства исправлять и в предыдущих этапах, не откладывая до E13.

Приёмка: полный сценарий «новый проект → уровень → проверка → сборка → запуск» воспроизводим по инструкции.
Состояние панелей восстанавливается; ошибки содержат понятное действие для исправления.
Сборка и тесты CI проходят на Windows/Linux/macOS; работоспособность UI и выпуска игры подтверждается
отдельно на каждой заявленной платформе, а не выводится из успешной компиляции.

### Порядок и границы

Основной порядок: E7 → E8 → E9 → E10 → E11 → отдельные срезы E12 → E13.
Зависимость, блокирующую пилот или выпуск, разрешено перенести раньше с записью причины в плане.
Графы материалов, VFX/частицы, катсцены, локализация, DLL-плагины на лету и стриминг больших миров
остаются вне текущего объёма. Их включение требует отдельного решения владельца.
Историческая отметка «E8» у выделения PF2e в разделе 2 не относится к новому этапу E8 этой дорожной карты.

Для каждого этапа: сохранить промпт, выполнить проверки затронутых возможностей, снять и просмотреть
BRP-скриншот, записать технический лог с доказательствами. Незавершённые проверки указывать явно;
статус PASS не присваивать только по наличию кода. После приёмки обновлять этот план и общую память.

## 9. Продуктовые направления и развилки модулей

Идеи добавлены по запросу владельца 2026-11-02. Это направления развития, а не уже реализованные возможности
и не обязательство одновременно разрабатывать три игры. Основная дорожная карта E7–E13 сохраняется.

### Существующий модуль: Pathfinder 2e

PF2e уже выделен в `crates/bevy_arc_pf2e` и подключается через `Pf2ePlugin` поверх редактора.
Он остаётся самостоятельным модулем: участники, правила, тактический бой и специализированный UI.
Повторно выделять его в модуль не требуется. Не переносить правила PF2e в универсальное ядро стратегии.
E7 по умолчанию использует этот существующий модуль как первый играбельный пилот.

### Ветка RTS: Mental Omega и интерфейс в стилистике C&C3

Идея: перенести игровой опыт Mental Omega на более современный интерфейс, используя C&C3 как ориентир
компоновки и взаимодействия. Не считать это решением о копировании ресурсов или совместимости движков.

Первая развилка — объём переноса:
- Только интерфейс и управление: отдельный прототип HUD, выделения, приказов и панелей производства;
  интеграцию с существующей игрой оценивать отдельно по доступным интерфейсам.
- Самостоятельный RTS runtime на Bevy: перенос правил, данных миссий и игрового поведения через отдельный
  адаптер, импорт ресурсов и поэтапную проверку соответствия. Это существенно больший проект.

Модули-кандидаты: RTS-приказы и группы выделения, движение отрядов, строительство базы,
очереди производства, ресурсы, боевой ИИ, туман войны, миссии и триггеры.
Специфичные правила Mental Omega держать в отдельном модуле поверх RTS-систем.
Редакторские инструменты: размещение юнитов/построек, зоны, маршруты, стартовые позиции и цели миссии.

Первый пилот: небольшая карта, выделение группы, приказ движения и атаки, одна постройка,
производство одного типа юнита и условие победы. Сначала определить нужный объём соответствия оригиналу.
Мультиплеер, синхронизация и воспроизведение матчей требуют отдельного решения до выбора модели симуляции.
До импорта внешнего контента зафиксировать источники, условия использования и допустимость распространения;
прототип интерфейса можно проверять на собственных временных ресурсах.

### Ветка универсальной стратегии

Идея: набор подключаемых механик для игр с глобальной картой и отдельным боем.
Disciples 2/3, Heroes of Might and Magic и King's Bounty — ориентиры разных вариантов геймплея,
а не игры, которые следует воспроизвести целиком, и не источники контента по умолчанию.

Модули-кандидаты:
- Глобальная карта: регионы/клетки, объекты, взаимодействия, владение территориями и переход в бой.
- Движение: маршруты, стоимость прохода, запас перемещения, посещение объектов и встречи армий.
- Экономика: ресурсы, доходы, расходы, требования и периодическое обновление.
- Поселения и постройки: развитие, зависимости, производство и найм.
- Герои и армии: состав, рост, инвентарь, способности и ограничения отрядов.
- Бой: отдельная сцена, расстановка, порядок действий, победа/поражение и возврат результата на карту.
- Кампания: задания, события, фракции, сохранение прогресса и последовательность сценариев.

Развилки выбираются профилем проекта, без жёсткой привязки к названию игры:

| Область | Варианты |
|---|---|
| Время на карте | Пошаговое; непрерывное с остановкой; одновременное планирование |
| Представление карты | Граф регионов; квадратная/гексагональная сетка; свободное движение |
| Управление | Герой с армией; несколько армий; самостоятельные отряды |
| Бой | Фиксированные позиции; тактическая сетка; свободное перемещение |
| Состав войск | Индивидуальные бойцы; стеки существ; смешанная модель |
| Развитие | Улучшение бойцов; развитие героя; найм и развитие поселений |
| Экономика | Владения и регулярный доход; сбор/добыча; награды и торговля |

Не реализовывать все сочетания сразу. Первый пилот использует один согласованный набор:
карта → перемещение армии → встреча → бой → награда/потери → возврат на карту → сохранение.
Вторая конфигурация проверяет, что общие контракты допускают другой стиль боя или экономики.
Приёмка: оба сценария настраиваются через редактор, используют собственный контент и переживают save/load.

### Общая основа и независимые правила

Общие сервисы-кандидаты: сцены и переходы, ассеты и префабы, команды, сохранение, события,
выделение, навигационные запросы и настройка UI. Переиспользовать существующие средства редактора.
Общность RTS и пошаговой стратегии проверять на реальных потребителях: одинаковое название механики
не означает одинаковую модель исполнения. Правила PF2e, RTS и стратегического боя остаются независимыми.
Новые крейты и универсальные интерфейсы вводить при подтверждённой потребности, а не по списку идей.
Каждый подключаемый модуль регистрирует свои компоненты, команды, панели и правила сохранения;
его отключение не должно ломать редактор и проекты без этого модуля.

Перед началом новой ветки зафиксировать: выбранный пилот, механику времени и боя, источники контента,
требования к совместимости, состав первого среза и критерий готовности. Приоритет веток выбирает владелец.

## 10. Продолжение интеграции Quillshade / Noodle — I2

2026-11-02 владелец разрешил публикацию проверенного каркаса и перенос отсутствующей у авторов мультифизики в следующий этап интеграции I2. Проверенные upstream HEAD совпадают с импортированными снимками; готового Biology/Granular/FluidFlow runtime в них нет. Noodle предоставляет редактор и пример point processing/instancing `geometry_nodes`, Quillshade — ассеты материалов и освещения.

I2 включает CPU backend и выполнение графов, typed parameters, PF2e effect adapter, dirty-region collision/Theta*, слоты материалов слоёв/водоёмов, persistent overrides/окружение и полную визуальную/hot-reload приёмку. Конкретные исходники, последовательность и критерии: [контракт интеграции, I2](08_quillshade_noodle.md#следующий-этап-i2-исполнение-графов-и-мультифизика). Публикация каркаса не означает выполнение I2; нумерация продуктовых этапов E7–E13 сохраняется.
